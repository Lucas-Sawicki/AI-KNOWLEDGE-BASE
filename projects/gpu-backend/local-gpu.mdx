## Cel

Lokalny backend GPU jest podstawowym środowiskiem wykonywania zadań AI, w szczególności workflow ComfyUI oraz przygotowania i treningu LoRA. Celem jest kontrolowane wykorzystanie VRAM, RAM, CPU i dysku, z jawnymi wejściami, parametrami, logami i artefaktami.

Dokument pomaga rozpoznać, czy GPU jest widoczne dla właściwego interpretera, uruchomić ComfyUI z wybranym urządzeniem, dopasować obciążenie do rzeczywistej pamięci oraz rozdzielić etapy LoRA. Nie ustala celów wydajnościowych ani uniwersalnych hiperparametrów (`NEEDS_VERIFICATION`).

**Status:** `REPORTED` — cel wynika z zasad repozytorium.

## Zakres i granice

W zakresie są lokalny Windows, ComfyUI, sterownik i runtime GPU, VRAM/RAM, lokalne artefakty, diagnostyka i testy. W zakresie jest ręczne przygotowanie do użycia zewnętrznego backendu, ale nie jego automatyczne uruchamianie.

Poza zakresem są: automatyczny fallback do Kaggle lub innej usługi, potwierdzanie bezpłatności, kosztów, limitów albo dostępności usług zewnętrznych, instalowanie lub modyfikowanie lokalnej instalacji bez analizy i zgody, wybór modelu lub hiperparametrów bez danych o GPU i modelu oraz przechowywanie sekretów w repozytorium.

Kaggle i inne usługi zewnętrzne wymagają osobnej decyzji oraz ręcznej weryfikacji dostępu, limitów, opłat, uwierzytelnienia i transferu danych (`NEEDS_VERIFICATION`).

**Status:** `REPORTED`; przyszła automatyzacja jest `PLANNED`.

## Architektura

```text
zadanie: workflow / trening / eksport
                  |
                  v
       manifest wejść i konfiguracja
                  |
                  v
        lokalny adapter GPU/ComfyUI
                  |
        +---------+----------+
        |                    |
        v                    v
   interpreter          sterownik + runtime
   ComfyUI                       |
        |                        v
        +------------->      lokalne GPU
                  |
          VRAM <-> RAM/CPU <-> dysk
                  |
          logi, checkpointy, eksport
```

Zadanie określa wejścia, artefakt i kryterium zakończenia. Manifest zapisuje ścieżki, model, workflow, parametry i wersje odczytane lokalnie. Adapter wskazuje interpreter i urządzenie, ale nie przełącza samoczynnie na Kaggle. Runtime obejmuje sterownik, bibliotekę obliczeniową, PyTorch lub inny używany runtime oraz ComfyUI. Warstwa artefaktów obejmuje logi, cache, checkpointy i eksport.

PyTorch rozróżnia pamięć zajętą przez tensory oraz pamięć zarezerwowaną przez caching allocator [1].

**Status:** `SOURCE_VERIFIED` dla mechanizmu PyTorch; `NEEDS_VERIFICATION` dla tej instalacji.

## Konfiguracja

Poniższy manifest jest szablonem dokumentacyjnym, nie istniejącym plikiem aplikacji. Wartości `null` i `[]` wymagają uzupełnienia lokalnie. Nie wpisuj sekretów.

```yaml
backend: local
comfyui_root: "E:\\AI AGENTS\\ComfyUI_windows_portable"
python_executable: "E:\\AI AGENTS\\ComfyUI_windows_portable\\python_embeded\\python.exe"
cuda_device: null
model_paths: []
workflow_path: null
input_dir: null
output_dir: null
checkpoint_dir: null
```

ComfyUI opisuje opcje `--cuda-device`, `--cpu`, `--lowvram`, `--highvram`, `--gpu-only`, `--cache-none`, `--output-directory` i `--base-directory` w swoim interfejsie CLI [2]. Nie wybieraj ich bez weryfikacji wpływu na konkretny model i GPU.

Dla kodu PyTorch można ograniczać widoczne urządzenia przez `CUDA_VISIBLE_DEVICES`, a urządzenie wybierać przez `torch.device` lub `torch.cuda.device` [1]. Zapisz w logu zarówno użyty identyfikator, jak i wynik diagnostyki, ponieważ ograniczenie widoczności wpływa na numerację procesu.

Nie ustalono tutaj wersji Pythona, PyTorch, CUDA, sterownika, ComfyUI, dtype, rozdzielczości, batch size, liczby kroków ani learning rate. Są zależne od instalacji, modelu lub GPU (`NEEDS_VERIFICATION`).

## Procedura użycia

### 1. Zdefiniuj zadanie

Zapisz identyfikator zadania, model bazowy, workflow lub skrypt, dane wejściowe, oczekiwany artefakt, kryterium zakończenia i lokalizację logu. Nie uruchamiaj zadania bez ustalenia miejsca wyniku.

### 2. Zweryfikuj ścieżki na Windows

Poniższe polecenia należy uruchomić na docelowym Windows, nie w tym repozytorium:

```powershell
$root = 'E:\AI AGENTS\ComfyUI_windows_portable'
$python = Join-Path $root 'python_embeded\python.exe'
Test-Path $root
Test-Path $python
& $python --version
```

Zapisz rzeczywisty wynik i wersję interpretera. `True` nie potwierdza zgodności GPU ani poprawnego uruchomienia (`NEEDS_VERIFICATION`).

### 3. Zbierz stan GPU i runtime

Dla NVIDIA, jeśli narzędzie jest dostępne:

```powershell
nvidia-smi
nvidia-smi --query-gpu=name,driver_version,memory.total,memory.used,memory.free --format=csv
```

Opcja `--query-gpu` i pola diagnostyczne są opisane oficjalnie [3].

Użyj tego samego interpretera, który ma uruchamiać zadanie:

```powershell
& $python -c "import torch; print('torch=', torch.__version__); print('cuda_available=', torch.cuda.is_available()); print('device_count=', torch.cuda.device_count()); print('device_names=', [torch.cuda.get_device_name(i) for i in range(torch.cuda.device_count())])"
```

Jeśli import lub wywołanie się nie powiedzie, zachowaj pełny błąd. Nie instaluj losowych pakietów i nie podmieniaj interpretera bez analizy.

### 4. Uruchom minimalny workflow

Użyj małego, znanego workflow i kontrolowanych danych. Oficjalne repozytorium ComfyUI opisuje uruchamianie i opcje CLI [2], ale ten dokument nie potwierdza konkretnej komendy dla wskazanej instalacji portable.

Przykład do dostosowania po sprawdzeniu struktury instalacji:

```powershell
Set-Location $root
& $python main.py --cuda-device 0
```

Powyższy przykład ma status `PLANNED`: obecność `main.py`, identyfikator `0` i akceptacja opcji wymagają lokalnej weryfikacji. Samo otwarcie interfejsu nie jest dowodem wykonania workflow. Zachowaj log, workflow, model, urządzenie i plik wynikowy.

### 5. Zarządzaj pamięcią

Dopiero po rozpoznaniu błędu dobieraj rozdzielczość, batch size, dtype, cache lub offload do konkretnego modelu i GPU. Nie podano uniwersalnych wartości. `torch.cuda.empty_cache()` zwalnia nieużywane bloki cache, ale nie pamięć zajętą przez żywe tensory [1]. Pojedyncza liczba z `nvidia-smi` nie wyjaśnia więc całego OOM.

## LoRA — cztery oddzielne etapy

### Przygotowanie danych

Zdefiniuj źródło, prawa do użycia, format, rozmiary, nazwy, opisy, filtrowanie, deduplikację, podział i manifest. Sprawdź, czy dane są czytelne dla wybranego narzędzia. Liczba obrazów, struktura katalogów i captioning zależą od modelu (`NEEDS_VERIFICATION`). Wynikiem jest nazwany zbiór oraz manifest, najlepiej z identyfikacją plików.

### Konfiguracja treningu

Wybierz model bazowy, implementację LoRA, rozdzielczość, batch size, learning rate, kroki/epoki, dtype, akumulację gradientu, seed, strategię pamięci i częstotliwość zapisu. Wszystkie ustawienia zależne od modelu/GPU/narzędzia są `NEEDS_VERIFICATION`; niezweryfikowane wartości są `PLANNED`. Zapisz manifest i rzeczywiste wersje przed treningiem.

### Checkpointy

Ustal osobno format, częstotliwość, nazewnictwo, katalog, retencję, wymagane miejsce i procedurę wznowienia. Checkpoint jest artefaktem pośrednim i nie jest automatycznie finalną LoRA. Test wznowienia wymaga kontrolowanego przerwania, ponownego odczytu i logu (`NEEDS_VERIFICATION`).

### Eksport

Ustal format finalny, metadane, kompatybilność z docelowym loaderem, nazwę, lokalizację i test ponownego załadowania. Nie podaję fikcyjnej komendy eksportu, bo zależy ona od narzędzia i modelu. Jeśli używany jest `safetensors`, zgodność formatu należy sprawdzić w jego oficjalnej dokumentacji [4].

**Status:** proces dla nieokreślonego narzędzia i parametrów: `PLANNED`; ustawienia zależne od modelu/GPU: `NEEDS_VERIFICATION`; brak podstaw do `LOCALLY_TESTED` bez raportu.

## Ograniczenia i ryzyka

- Kompatybilność zależy od GPU, sterownika, runtime, modelu, wersji bibliotek i instalacji.
