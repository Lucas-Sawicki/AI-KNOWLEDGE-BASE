# Indeks wspólnej wiedzy technologicznej

> **Status indeksu:** `SOURCE_VERIFIED` dla zakresu, zasad i inwentaryzacji wynikających z repozytoryjnych plików `AGENTS.md` i `README.md` odczytanych podczas przygotowania tego dokumentu. Status nie oznacza, że każda procedura opisana w dokumentach docelowych została wykonana lub przetestowana. W tym indeksie nie deklaruje się `LOCALLY_TESTED`.

## Cel

Ten dokument jest punktem wejścia do wspólnej wiedzy technologicznej repozytorium `AI-KNOWLEDGE-BASE`. Ma pomóc agentowi AI szybko ustalić, gdzie szukać informacji wspólnych dla wielu projektów, jakie źródło ma pierwszeństwo oraz które ustalenia wymagają weryfikacji.

`knowledge/` przechowuje zasady i wiedzę możliwą do ponownego użycia między projektami. Szczegóły konkretnego projektu należy pozostawić w `projects/`. Kryteria jakości, bezpieczeństwa i testowania należy utrzymywać w `standards/`, a powtarzalne struktury dokumentów w `templates/`. Nie kopiuj szczegółów projektowych do tego indeksu.

## Zakres

Indeks obejmuje:

- mapę istniejących obszarów i wpisów repozytorium;
- reguły wyboru źródeł oraz oznaczania pewności informacji;
- procedurę użycia wspólnej wiedzy przez agenta;
- wymagania dokumentowania, testowania i diagnostyki;
- ograniczenia dotyczące aktualności, środowiska i publikacji.

Indeks nie jest:

- dokumentacją konkretnego projektu, instalacji Windows, modelu, workflow ani skryptu;
- dowodem wykonania instalacji, inferencji, testu integracyjnego lub testu na lokalnym środowisku;
- implementacją standardu ani gwarancją działania API w określonej wersji.

4. Nie wymyślaj nazw API, parametrów, wersji, skryptów, wyników ani zależności.
5. Oficjalne źródło opisuje możliwości i wymagania, ale nie potwierdza działania w konkretnym środowisku bez testu.
6. Nie zapisuj sekretów, tokenów, haseł ani prywatnych konfiguracji.

## Jawne statusy

Każdy istotny wpis, procedurę lub wynik oznacz jednym albo kilkoma statusami zgodnie z ich znaczeniem:

- `SOURCE_VERIFIED` — twierdzenie potwierdzone w podanym źródle oficjalnym albo w repozytoryjnych instrukcjach; nie oznacza testu lokalnego.
- `REPORTED` — informacja zgłoszona lub zaobserwowana, której nie potwierdzono w tym wpisie źródłem lub testem.
- `NEEDS_VERIFICATION` — wymaga sprawdzenia w konkretnym środowisku, wersji, konfiguracji, modelu albo kodzie.
- `PLANNED` — plan, propozycja lub szablon do wykonania; nie jest wynikiem wykonanej operacji.
- `LOCALLY_TESTED` — wolno użyć wyłącznie po rzeczywistym teście lokalnym z zapisanym środowiskiem, poleceniem, oczekiwaniem i wynikiem. Ten indeks nie deklaruje tego statusu.

Jeżeli twierdzenie ma kilka aspektów, oznacz je osobno. Na przykład oficjalny opis API może być `SOURCE_VERIFIED`, natomiast użycie tego API z konkretną wersją modelu powinno pozostać `NEEDS_VERIFICATION` do czasu sprawdzenia.

- podawać wymagania środowiskowe bez dopisywania niezweryfikowanych wersji;

- zawierać procedurę testowania, diagnostykę i znane ograniczenia;
- mieć źródła oficjalne przy twierdzeniach zewnętrznych;
- oznaczać każdy niepotwierdzony element jednym z `REPORTED`, `NEEDS_VERIFICATION` lub `PLANNED`;
- nie deklarować `LOCALLY_TESTED` bez rzeczywistego, udokumentowanego testu.

## Procedura użycia przez agenta AI

1. Odczytaj ten indeks oraz `AGENTS.md` i `README.md`.
2. Określ, czy zadanie dotyczy wiedzy wspólnej, konkretnego projektu, standardu czy szablonu.
3. Otwórz właściwy wpis i jego źródła; nie traktuj samej obecności pliku jako potwierdzenia treści.
4. Rozdziel informacje `SOURCE_VERIFIED`, `REPORTED`, `NEEDS_VERIFICATION` i `PLANNED`.
5. Porównaj wymagania z rzeczywistym kodem, interpreterem, wersjami bibliotek i konfiguracją docelową, jeśli masz do nich dostęp.
6. Wykonaj minimalny test opisany w dokumencie docelowym albo oznacz wynik jako `PLANNED`/`NEEDS_VERIFICATION`; nie deklaruj sukcesu bez wyniku.
7. Zapisz ustalenia w odpowiedniej warstwie, unikając kopiowania wspólnej wiedzy do dokumentu projektu.
8. Przed publikacją sprawdź zakres zmiany, źródła, statusy, sekrety i zgodność z procesem zatwierdzenia użytkownika.

## Testowanie i zapis wyników

Status testów tego indeksu: `PLANNED`. Nie wykonano testów bibliotek, instalacji, integracji, inferencji ani testów lokalnego Windows. Nie deklaruje się `LOCALLY_TESTED`.

Dla każdego rzeczywiście wykonanego testu zapisz co najmniej:

- datę i środowisko;
- użyty interpreter, wersje i backend, jeśli mają znaczenie;
- polecenie lub minimalną procedurę;
- oczekiwany rezultat;
- rzeczywisty rezultat i istotny log błędu;
- status po teście.

Sama składnia dokumentu lub obecność ścieżki w repozytorium nie jest testem działania biblioteki, aplikacji ani środowiska.

## Diagnostyka

W przypadku sprzeczności lub błędu:

1. sprawdź, czy agent czyta właściwy wpis i źródło;
2. sprawdź status informacji i datę jej weryfikacji;
3. porównaj dokumentację z faktycznym kodem i środowiskiem;
4. zweryfikuj interpreter oraz wersje zależności, nie zakładając, że dwa środowiska Pythona są tym samym środowiskiem;
5. odtwórz minimalny przypadek i zapisz wynik;
6. jeśli nie można sprawdzić przyczyny, pozostaw `NEEDS_VERIFICATION` zamiast zgadywać.

Dla lokalnego Windows agent nie powinien twierdzić, że odczytał lub zmodyfikował lokalną ścieżkę bez autoryzowanego dostępu. Należy przygotować dokładną komendę lub skrypt do uruchomienia przez użytkownika i poprosić o wynik.
